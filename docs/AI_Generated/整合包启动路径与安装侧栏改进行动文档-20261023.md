日期：2026-10-23。本文针对本次提出的五项改进记录分析结果和后续改动方案。用户本次指令以“说明执行”结尾，因此本次仅新增本文，不修改项目代码，也不修改用户已安装的实例。

## 一、启动崩溃的定位结果

### 1. 错误链与实际配置位置

读取了用户提供的日志：

- `C:/Users/wwwin/OneLauncher/installed/minecraft/logs/latest.log`。
- 日志末尾指向的崩溃报告：`C:/Users/wwwin/OneLauncher/installed/minecraft/instance/6a710be5/crash-reports/crash-2026-10-23_17.53.27-client.txt`。

日志中此次启动使用 Minecraft 1.20.1、Forge 47.4.28，`--gameDir` 指向实例 `instance/6a710be5`。17:53:27 的三次 `ScreenCustomization.readCustomizableScreensFromFile` 调用先出现 `java.io.IOException: 系统找不到指定的路径`，栈上涉及 `File.createNewFile`。随后，FancyMenu 3.7.0 的 `customizableScreens` 仍为 null，Drippy Loading Screen 3.0.12 初始化加载画面时调用该对象，导致空引用和 `ExceptionInInitializerError`。

已只读核对安装文件和模组字节码：

- 实例内的 `config/fancymenu/customizablemenus.txt` 存在。
- 游戏根目录下的 `config/fancymenu` 不存在。
- 使用 `javap` 检查实际安装的 FancyMenu JAR，确认其配置文件通过 `new File("config/fancymenu/customizablemenus.txt")` 创建，使用的是相对路径；文件缺失时直接调用 `createNewFile()`。

崩溃报告中 Connector、Embeddium 的提示是模组生成的诊断文本，仅作为附件内容参考，不视为用户要求卸载模组或报告问题的指令。此次异常链已有更直接的路径证据。

### 2. 对应的启动器问题

`OneLauncher.Core/DefaultComponent/Launcher/GameLauncher.cs` 第 49 行把游戏目录设置为 `useRootMode ? gameRootPath : gameData.InstancePath`；第 77 行却固定把 Java 进程的 `WorkingDirectory` 设置为 `Init.GameRootPath`。

因此普通实例启动时，`--gameDir` 和 Java 工作目录不一致。FancyMenu 的相对配置路径落到根目录，而导入器已经把整合包配置复制到了实例目录。这能解释此次“配置已导入，但创建配置文件找不到父目录，继而加载画面崩溃”的完整错误链。

后续将修正这处目录错位。修正后的完整游戏启动仍需复测，当前分析不能保证该整合包没有其他独立兼容问题。此次日志没有支持扩大为加载器版本安装改造的证据。

## 二、五项改进的具体操作

### 1. 下载版本侧栏应用现有状态图标

调整 `DownloadPane` 的下载状态卡片，参照 `InstallPackPane` 中截图所示的样式，在状态文字左侧放置固定 18×18 的 `PathIcon`。复用已有的完成勾选圆形、运行时钟、失败警告、取消叉号几何，不新增图片资源。

保留 `PaneHeader`、`pane-divider`、`pane-surface`、`pane-status` 和 `pane-progress`。状态边框、浅底色、图标和文字使用现有 `AccentBrush`、`AccentHoverBrush`、`SuccessBrush`、`SuccessSubtleBrush`、`DangerBrush`、`DangerSubtleBrush`、`WarningBrush`、`WarningSubtleBrush` 等主题资源，在下载视图内按状态应用；不增加重复颜色或重新加载全局样式。

`DownloadPaneViewModel` 增加下载状态及对应的图标、文字和操作状态通知。等待、运行、取消中、已取消、失败、已完成都由实际任务流程更新，任务中心取消也同步到侧栏；结束时解除本次事件订阅，避免重试后的旧任务回调覆盖新状态。

同时修正一个与完成图标直接相关的问题：目前下载进度回调收到 `DownProgress.Done` 就调用 `task.SetDone()`，但此后才登记实例、设置默认实例。后续把任务完成、100% 和完成图标统一放到这些操作成功之后；安装组件的 Done 回调只表示文件安装阶段结束。取消或登记失败不能显示成功，排队中的旧进度不能覆盖终态。此次仅改前端下载 ViewModel，不改 Download 组件。

### 2. 确认整合包任务中心接入

已确认整合包安装接入的是共享任务中心：

- `InstallPackPaneViewModel.ToInstall()` 第 147 行调用 `_unitedCore.TaskManager.CreateTask(...)`。
- 同一任务接收 `SetProgress`、`SetDone`、`SetFailed` 和 `Cancel`。
- `TaskCenterPaneViewModel` 使用同一个 `UnitedCore.TaskManager`，订阅 `OnTaskCreate` 并读取队列；任务条目订阅进度、完成、失败、取消事件。
- 整合包侧栏已经订阅当前任务的 `Canceled`，任务中心的取消按钮调用同一 `TaskInstance.Cancel()`。
- 开始和完成通知携带 `openTaskCenterAfterClick: true`。

已有链路应保留，不重复创建任务管理器或增加第二个安装任务。后续补充真实任务中心 ViewModel/AXAML 的联动验证，覆盖任务中心在安装前已经打开和安装后才打开两种情形。

侧栏打开时的整合包信息预览使用自己的取消令牌，当前不创建任务中心条目；点击“安装”后才创建安装任务。新增的图标下载放在该安装任务内。任务中心接入不等同于安装后验证游戏能够启动，两者应分别验收。

### 3. 安装与取消按钮参考下载侧栏

将 `InstallPackPane` 和共用的 `InstallModPane` 底部操作区改为下载侧栏已有的双列 Grid：`ColumnDefinitions="*,*"`、`ColumnSpacing="10"`，左侧取消、右侧开始安装。沿用 `pane-danger` 和 `pane-primary`，按钮等宽、固定在可滚动内容区之外。

安装前保留两个按钮位置，取消禁用；信息加载或安装中，开始安装禁用，取消按现有可执行条件启用；取消发出后显示“正在取消…”并禁用重复取消。整合包成功后右侧同一位置显示“完成”，执行关闭，左侧取消禁用。失败或取消退出后，按现有能力允许重试。信息加载失败时，“重新加载信息”保留为辅助操作，不挤占主操作的左右位置。

以命令的 `CanExecute` 和 ViewModel 状态控制按钮，不照搬下载视图通过另一个按钮的 `IsEnabled` 反向绑定取消按钮的写法。保留共用安装侧栏的实例选择、依赖选项和只读倒序版本列表。

### 4. 统一 Java 工作目录与游戏目录

在 `GameLauncher.BasicLaunch()` 中计算一次本次游戏目录，并同时用于 `SetGamePath(...)` 和 `ProcessStartInfo.WorkingDirectory`：

```csharp
var launchGamePath = useRootMode ? gameRootPath : gameData.InstancePath;
```

普通启动使用实例目录，根目录模式继续使用根目录。只修正 Java 工作目录，不迁移用户配置，不在游戏根目录补建 FancyMenu 配置，也不删除或更换整合包里的模组。

核对共享资源仍使用原有游戏根目录绝对路径：`libraries`、`assets`、版本主文件、natives、日志配置和加载器参数不能因工作目录变化而丢失。带空格路径、两个实例相对配置隔离及根目录模式都要验证。

### 5. 从 Modrinth 安装的整合包自动设置实例图标

搜索结果已经将 Modrinth 的图标 URL 保存到 `ResourceItem.IconUrl`。现有实例图标文件是 `<InstancePath>/.olc/customicon`；`GameDataItem.GetGameDataIcon()` 已优先读取该文件，主页和编辑实例侧栏也复用此入口，读取失败会回退到默认图标。

后续将图标 URL 从 `InstallPackPaneViewModel` 传给 `ResourceInstallerService.ImportModpack`，在现有参数之后增加可选参数，保持既有无图标调用兼容。下载图标复用现有 HTTP 客户端，并使用当前安装任务令牌。

此前明确限制修改 `ModpackImporter` 等组件，且导入器当前只返回 Task，不返回创建的实例。本方案在这些限制内复用原有覆盖文件机制：

1. 取得图标后，为已经下载并校验过的临时 `.mrpack` 创建本次安装专用的唯一临时副本。
2. 在副本加入 `overrides/.olc/customicon`，如该固定条目已存在，则替换该条目，避免重复 ZIP 条目。
3. 把副本和原来预览所用的同一个 `MrpackParser` 交给原导入入口。`modrinth.index.json` 保持原样。
4. 导入器原有 overrides 复制流程会把图标放进本次创建的实例，并在实例登记前完成写入，实例列表第一次收到数据更新就能读取图标。
5. 安装副本在服务的 finally 中清理；原临时包仍由 `ModpackDownload` 管理，供失败或取消后的重试复用。

原始包的 SHA1 校验仍只针对服务器下载内容；加入启动器图标后的本地副本不再冒充原始文件参与该哈希校验。没有图标时直接走原导入流程，不创建额外副本。图标缺失、HTTP 失败或响应不是有效图片内容时保留包内原图标或默认图标，给出简短提示，不让可选图标下载失败阻止安装；任务取消仍正常传播，不能被当成可忽略的图标错误。

这样无需修改导入器的返回值，也无需按实例名称或安装前后列表差集猜测目标，多个整合包并发安装时图标能随各自包副本进入正确实例。只对启动器资源页面发起的新安装应用 Modrinth 图标，本地导入和已经存在的实例不做追溯替换；用户之后仍可通过原编辑入口更换图标。
