## 1. 结论与已接受的排查结果

用户已经排查并明确：

```csharp
servises = Init.InitTask.GetAwaiter().GetResult();
```

不是此次启动卡顿的原因。本文据此排除该行作为启动根因，后续方案不以改写它、调整 `Init` 或改动 Desktop 启动入口为前提。此前仅根据同步等待形式将其判定为本次根因的结论撤回。任务已完成时，`GetResult()` 可以立即返回；是否阻塞必须结合现场状态判断。

目前能够从源码确认的是：

| 场景 | 代码事实 | 当前判断 |
|---|---|---|
| 打开主窗口 | `MainWindow.OnOpened` 在同一次 UI 回调中创建首页和其余七个页面及其 ViewModel | 明确存在集中的同步初始化工作，是启动部分的优先调查对象；尚无耗时数据确定哪个步骤占主导 |
| 设置页初始化 | 构造函数通过生成属性加载配置，多个 Changed 回调会调用 `DBManager.Save()` | 明确存在初始化时的额外保存及事件刷新，可能放大首屏负载 |
| 账户、实例、服务器列表 | 列表构建发生在 UI 线程，列表项同步读取并解码本地图标或默认图片 | 明确存在同步图片工作；实际耗时取决于数量、图片大小及存储状态 |
| 点击整合包侧栏安装 | 后端在异步方法内部同步执行整个 `ZipFile.ExtractToDirectory` | 明确的 UI 阻塞路径；包大或文件多时影响更明显 |
| 点击资源卡片安装 | 打开侧栏后加载包信息，下载结束后的 ZIP 打开和清单解析仍是同步操作 | 存在另一条可能的 UI 停顿路径，须区分它与侧栏开始导入按钮 |
| 任务栏图标消失 | 主窗口仍指定 ICO，窗口和 EXE 图标文件内容一致，未找到主窗口隐藏或清空图标的代码 | 原因未证实，不能仅凭图标消失确认是哪段代码阻塞 |

`async`、`await` 和返回 `Task` 不等于自动把整个方法放到工作线程。遇到真正尚未完成的异步等待之前，同步代码仍由调用线程执行；等待之后也可能回到 UI 上下文。将同步工作放进 `Dispatcher.UIThread.InvokeAsync` 仍是在 UI 线程执行。

## 2. 启动调用链与需要测量的位置

当前路径为：

```text
App.OnFrameworkInitializationCompleted
  → new MainWindow
  → MainWindow.OnOpened（UI 线程）
      → HomePageViewModel
      → version + VersionPageViewModel
      → account + AccountPageViewModel
      → ModsBrowser + ModsBrowserViewModel
      → download + DownloadPageViewModel
      → settings + SettingsPageViewModel
      → gamedata + GameDataPageViewModel
      → server + ServerPageViewModel
```

依据为 `OneLauncher/Views/MainWindow.axaml.cs:105`。每个步骤都包括视图构建、依赖解析、构造函数和可能立即执行的列表刷新。当前打开首页时，未访问的页面也全部初始化。

### 2.1 设置构造过程触发保存

`OneLauncher/ViewModels/Pages/SettingsPageViewModel.cs:352` 的构造函数设置以下生成属性：

- `LeftButtonListSpacing`；
- `IsM1`、`IsM2` 或 `IsM3`；
- `MaxDownloadThreadsValue`、`MaxSha1ThreadsValue`；
- `IsSha1Enabled`；
- `SelectedDownloadSource`。

这些属性变化会进入对应的 `On...Changed` 回调并保存配置。是否触发取决于原字段值与读取值是否相同，因此不应声称每次都固定保存同样的次数。

`OneLauncher.Core/Global/ModelDataMangers/BasicDataManger.cs:90` 显示：保存包含文件创建、序列化、替换及 `NotifyDataChanged()`。多个保存会经现有锁串行执行，但仍会产生多个通知。主窗口收到通知后排队应用 UI 设置；已经构建的服务器页收到配置通知后会再次重建服务器列表。这不是配置读取所必需的行为。

后续应记录设置页构造前后的保存次数、数据事件次数，以及这些事件是否落在实际卡顿区间。

### 2.2 列表项同步解码图片

- `AccountPageViewModel.RebuildList` 在 UI 线程构造 `UserItem`，同步打开本地玩家图片或默认图片。`UserItem.HeadImg` 的字段初始化已经加载默认图片，随后对象初始化器又指定一次 `HeadImg`，存在重复解码和未使用图片对象。
- `GameDataPageViewModel.RefList` 把整个列表构建放进 UI Dispatcher；`GameDataItem` 构造函数调用 `GetGameDataIcon`，同步读取 `.olc/customicon` 或默认图片。
- `ServerPageViewModel.RefList` 在 UI Dispatcher 中调用 `RebuildList`；`ServerIconLoader.Load` 同步读取和解码服务器图片。
- 首页设置默认实例时，属性回调加载图标；构造末尾又调用一次 `GetGameDataIcon`，存在重复加载的可能。

这些事实说明首屏可能把所有实例、账户与服务器的图片成本集中支付。还需测量图片解码、列表构建和视图加载各自耗时，不能直接把全部卡顿归因于图片。

### 2.3 其他测量对象

首页会提前发起联机组件初始化、新闻读取和更新检查；资源检索页构造时会开始搜索。网络等待本身不能直接等同于 UI 阻塞，需要检查实际同步片段和回到 UI 的处理。

`Tools.GetFileMD5Async` 使用异步哈希，不据此将联机校验判为长时间同步阻塞。`VectorIcons` 首次使用时集中解析九个 Geometry，可列入首次加载测量，但当前没有证据把矢量资源迁移判为根因。

## 3. 整合包按钮的阻塞路径

### 3.1 侧栏开始安装

```text
InstallPackPaneViewModel.ToInstall（UI 线程）
  → 可选图标获取
  → ResourceInstallerService.ImportModpack
  → ModpackImporter.ImportFromMrpackAsync
  → ModpackImporter.RunImportAsync
  → ZipFile.ExtractToDirectory（同步解压整个包）
  → 创建实例、应用覆盖文件、下载与登记
```

源码位置：

- `OneLauncher/ViewModels/Panes/InstallPackPaneViewModel.cs:151`；
- `OneLauncher.Core/Services/ResourceInstallerService.cs:26`；
- `OneLauncher.Core/DefaultComponent/Resource/Pack/ModpackImporter.cs:71`，同步解压位于第 75 行。

当前调用方直接 `await` 后端导入；导入内部在解压前没有让出同步工作。没有图标时，图标方法可以立即返回，点击后就直接进入解压；存在图标时，解压通常发生在图标下载完成后。这说明必须区分“点击时立即停顿”与“图标阶段结束后停顿”。

导入末尾 `Dispose()` 还会递归删除临时解压目录。如果后端始终沿 UI 上下文执行，结束阶段也可能卡顿。应将整个既有导入调用放到工作线程，而非只把单独一行 ZIP 解压移出去。

### 3.2 资源卡片打开侧栏

`ModsBrowserViewModel.ToInstallResource` 构建侧栏后调用 `LoadInfo`。`GetModpackModrinth.GetAsync` 异步下载包文件，然后同步打开 ZIP 并通过 `MrpackParser` 解析清单。该路径尚未导入实例，但同步解析仍可能占用 UI。

侧栏中的可选图片验证也使用同步 `new Bitmap(stream)`；成功后的图标写入还包含目录创建和文件替换。是否为明显耗时需单独测量。

### 3.3 创建任务时的次要路径

`TaskManager.CreateTask` 同步触发 `OnTaskCreate`；若任务中心已打开，`TaskCenterPaneViewModel.OnTaskCreate` 在 UI 线程直接重建整个任务队列。任务较多时，这段工作可能发生在按钮点击的最开始。应对比任务中心打开/关闭、任务队列少/多的情况，确认后再做局部调整。

## 5. 后续行动顺序

### 第一步：测量启动阶段，再决定具体修复范围

使用工作区内的隔离检查环境，分别记录：主窗口构造、每个页面视图构建、ViewModel 依赖解析、列表刷新、图片解码、设置初始化引发的保存与通知。

同步记录 UI 消息调度延迟。既要看方法自身耗时，也要看排队到下一轮 UI 的工作；不能仅用应用总启动时间判定根因。此处接受用户对 `GetResult()` 的排除结果。

### 第二步：缩小首屏初始化工作

若测量证实 `OnOpened` 的页面集中构建对应卡顿，首页先完成初始化；其余页面在首次导航访问时创建并缓存，继续复用现有单例 ViewModel 与工厂。检查隐藏页面回退、消息回调、任务中心和未创建页面引用。

视图及控件构建仍在 UI 线程。不能把 `InitializeComponent()` 或全部 ViewModel 构建直接包进 `Task.Run`。仅将全部页面初始化延迟一次、或添加 `Task.Yield()`，也不能消除其中的同步重活。

设置页初始化改为读取并初始化字段，避免用会保存配置的交互属性回调加载旧值。用户实际修改设置时仍走原有保存逻辑。此项即使设置页改为按需创建，也应避免把保存与刷新成本转移到首次点击设置时。

如果图片测量仍显示明显阻塞，再局部调整已确认的加载点，去掉重复解码，分离文件读取/解码与 UI 列表赋值，并明确图片对象的持有和释放。首轮不引入全局图片缓存框架。

### 第三步：在前端调用处隔离整合包工作

在 `InstallPackPaneViewModel` 中，信息获取和导入调用通过 `Task.Run` 执行现有后端 API，调用方 `await` 结果后再更新 UI。传入同一个任务取消令牌，保持包对象在后台工作结束前存活。

`Progress<T>` 在 UI 线程创建；后台仅调用后端和报告进度。侧栏属性、通知、任务终态和已导入实例引用在 UI 线程处理。保留已有任务身份检查、重复安装防护、取消后等待退出及关闭侧栏后的包文件清理顺序。

首页本地 `.mrpack` 导入也使用相同调用边界，避免只修资源侧栏而保留另一条同步解压路径。

此方案使用现有可调用后端，不新增后端业务接口，也不复制解压、清单筛选或安装逻辑到 UI。

`Task.Run` 和传入取消令牌不会中断已经执行中的 `ExtractToDirectory`。目标是释放 UI，让取消按钮能及时响应；解压过程的即时取消和回滚属于导入器的另一项改造，不能宣称已随本方案解决。

### 第四步：只处理测量确认的剩余停顿

对图标解码、图标写入和任务中心整队列刷新分别测量。确有明显成本时，将纯文件工作移出 UI，或将任务中心创建事件的刷新合并排队；控件和绑定更新仍回到 UI。不要凭名称或猜测修改渲染后端、矢量图标或窗口图标。

## 7. 验证计划与完成标准

所有检查使用项目内隔离配置。测试输出、HTTP 替身、脚本、包文件、解压目录和启动器生成文件均放在 `build/ui-responsiveness-20261023` 下；执行进程的 `TEMP`、`TMP` 指向该目录内的临时子目录，以覆盖后端使用 `Path.GetTempPath()` 的位置。不得以真实用户实例作为自动测试数据。

1. **启动定位**：比较每个阶段耗时与 UI 调度延迟，得到具体成本归属。检查首页先显示、首次导航创建、再次访问复用及隐藏页面回退。
2. **配置初始化**：构建设置页只读取配置，不产生额外保存/数据变更通知；真实修改后仍正确保存并更新相关界面。
3. **安装响应性**：用可控的进度门限在“正在解压”报告处暂时阻止后台流程，确认 UI 仍可处理排队操作和取消；使用包含覆盖文件的包验证实际导入正确。覆盖图标缺失与存在的两种起始路径，以及首页本地导入。
4. **取消与生命周期**：取消后不登记尚未完成的实例；已经登记后的取消不允许重复安装；关闭侧栏等待后台退出后才删除包；迟到进度不能覆盖终态。
5. **现有回归**：整合包、下载侧栏、模组/光影、导航、通知任务中心和依赖图检查按影响范围执行。项目指定测试项目为 ConsoleTest；相关后端兼容检查使用其已有 `--protocol` 入口，UI 响应性使用现有 Headless 回归项目，避免 ConsoleTest 普通入口初始化真实用户配置。
6. **任务栏图标**：Headless 只能验证资源和窗口属性，实际任务栏必须在 Windows 桌面运行时观察。记录卡顿前、卡顿中和恢复后的图标状态，确认是否与 UI 无响应同步，不能用 Headless 截图替代这一结论。

完成标准是：找到启动时实际占用 UI 的步骤；整合包预览和导入的同步文件工作不占用 UI；首屏不提前支付未访问页面的初始化成本；设置页初始化不额外保存；取消、错误、任务中心和实例图标行为回归通过。图标问题若持续存在，应单独给出运行证据及修复范围。

### 9.1 ConsoleTest 被发布的直接原因已经查明

`OneLauncher.sln:12` 包含 ConsoleTest 项目；第 101、103、105、107、109 行分别启用了其 Release 配置的 `Build.0`。ConsoleTest 不是刚刚临时塞入解决方案的项目，其项目文件历史至少追溯到 `1182d99`（2025-05-31）。

发布解决方案时，ConsoleTest 作为一个独立可执行项目进入发布范围。

同时，`Directory.Build.props:15` 和第 17 行根据 PublishProfile 名称，从 Desktop 目录导入共享发布配置，导入条件没有把范围限制为 Desktop 及其生产依赖。ConsoleTest 因而也会导入 WindowsAot：

```text
发布 OneLauncher.sln / 根目录解决方案
  → ConsoleTest 也属于解决方案发布范围
  → ConsoleTest 导入 Directory.Build.props
  → 导入 OneLauncher.Desktop 的 WindowsAot.pubxml
  → PublishAot=true，PublishTrimmed=true，RuntimeIdentifier=win-x64
  → PublishDir 根据 ConsoleTest 自己的 MSBuildProjectDirectory 计算
  → ConsoleTest/bin/Release/net10.0/publish/win-x64/aot
```

这与用户日志中的路径完全对应。ConsoleTest 的反射检查及非源生成 JSON 序列化不适用于完整裁剪/AOT，所以额外出现 IL2026、IL2075、IL3050 警告。Desktop 才导入 `build/PublishValidation.targets` 的发布保护；ConsoleTest 未导入该文件，因此自己的这些警告没有按同样规则导致发布失败。

`OneLauncher.Desktop/OneLauncher.Desktop.csproj:15` 的引用是 `OneLauncher.Console`，第 16 行引用 `OneLauncher`；这两个项目再引用 Core。没有指向 ConsoleTest 的项目引用，也没有发现通过自定义构建 Target 启动 ConsoleTest 的配置。

```text
OneLauncher.Desktop
  ├─ OneLauncher.Console → OneLauncher.Core
  └─ OneLauncher         → OneLauncher.Core

ConsoleTest → OneLauncher.Core（独立项目）
```

因此，ConsoleTest 是单独被解决方案发布，并没有被作为 UI 依赖编译进 Desktop。用户给出的 40.3 秒 ConsoleTest 发布时间说明存在额外发布工作；并行构建时不能直接从总耗时减去这个数值估算节省时间。
