## 3. 已确认的功能缺口

以下均为源码分析结果，未通过实际导入、导出实验复现。

### 3.1 清单指定的加载器版本没有完整传递

`GetLoaderInfo()` 返回加载器类型与版本，导入器用该版本判断能否复用已有安装；但 `InstallBaseGameAsync` 不接收这个版本，创建 `DownloadInfo` 时也没有传入版本配置。

Fabric、Quilt Provider 在未指定版本时选取元数据中的第一项。Forge、NeoForge Provider 已有指定版本分支，但 `DownloadInfo.Create` 没有传入并赋值对应参数；Quilt 尚无指定版本字段。由此可能出现“包要求某加载器版本，实际安装另一版本”。

此外，基础安装默认会附加 Fabric API 或 QSL。整合包自身已定义文件时，应关闭这些自动附加选项，避免额外安装包未指定的模组，或覆盖包内文件。

加载器元数据按 `versions/<Minecraft版本>/version.<加载器>.json` 共享；`GameData` 未保存独立加载器版本。不同包要求同一 Minecraft 版本的不同加载器版本时，存在共享元数据被替换的风险。应在执行前确定冲突处理策略，不能只传版本后就声称实现了多版本共存。

### 3.2 清单与文件校验不足

- 模型虽然声明 `formatVersion`、`game` 等属性，解析器未验证其取值和关键字段完整性；显式 null 的集合或空版本信息可能在后续流程中产生普通异常。
- 文件使用 `Downloads.FirstOrDefault()`，只选第一个地址，没有空地址校验或备用地址回退。下层 `DownloadFile` 遇到空 URL 会直接返回，缺失文件可能被当作处理完成。
- 目标文件存在就跳过下载，没有验证大小或哈希；导入器也没有调用 `CheckAllSha1`，无法发现已有坏文件或错误下载。
- 文件路径越出实例目录时，解析器直接跳过该项。虽然已有目录边界检查，但静默跳过会使坏清单看起来导入成功；应改为明确报错并验证路径合法性。
- 文件大小模型使用 `int`；若支持较大文件，应与下载模型一起核对数值范围，而不是仅在此处强制转换。
- 当前只复制 `overrides`，模型没有环境字段，也没有客户端、服务端文件区分。后续应按官方 `.mrpack` 规范核对 `env`、`client-overrides`、`server-overrides` 等行为后补齐。此次联网文档读取失败，未完成规范兼容性核验。

不要把现有 `ResourceFileInstaller` 直接接入后就当作全部解决：它可复用存在检查、SHA1 和取消检查，但不能替代清单有效性、环境筛选、备用 URL 与覆盖文件优先级的设计。

### 3.3 取消、失败与实例提交

导入会先创建实例目录，最后调用 `AddGameDataAsync`。`Dispose` 只清理临时解压目录，失败或取消可能留下未登记的实例文件。

首页把导入任务定义在 try 内部；catch 只显示异常，没有把导入失败映射到 `task.SetFailed`，也没有独立处理取消。`TaskInstance.SetProgress` 不限制终态，迟到的进度回调仍可能修改已取消、已完成任务的显示。

解压是同步 `ZipFile.ExtractToDirectory`，取消检查在解压结束之后。`DownloadInfo.Create` 的元数据准备也没有取消令牌参数。现有下载批处理是在每个文件下载前增加计数，不能直接把该计数解释为文件已经下载完成。

后续应保证成功才登记新实例、失败只清理本次新建实例的内容，不删除复用的共享游戏文件。登记时还要核对 `AddGameDataAsync` 的内存更新与保存失败行为，设计明确的回滚边界。

### 3.4 导出范围与版本写入

导出已有相邻临时文件、完成后移动及失败清理机制，可保留复用。不过目前枚举几乎整个实例，仅排除本次输出文件、临时文件和根清单。日志、存档、旧的其他 `.mrpack` 文件等可能被一起打包。

应明确“可分享的整合包”与“完整实例备份”的文件范围，设计可见的导出选项和默认排除规则。默认至少避免把历史导出包、临时下载和日志递归带入新包。

导出器获取加载器版本时优先读 `loader.version`，否则直接返回元数据 `id`。应核对 Forge/NeoForge 的 `id` 是否为清单要求的版本标识，避免写入整段启动配置 ID。当前 `files` 被省略、全部内容放入 overrides 的方式也需核对格式兼容性，不能只验证本启动器能解析。

导出方法支持进度和取消，但 UI 只调用 `ExportAsync(editingGameData)`，没有创建任务、传递进度或令牌。

## 4. 建议的后续实施顺序

### 阶段 A：只执行目录迁移

执行第 2 节的四个文件迁移与三个前端引用修正。独立编译验证，生成迁移执行报告。该阶段无需改变整合包业务、全局资源类型或前端界面。

### 阶段 B：修正现有本地导入、导出

1. 给解析器增加结构、版本、文件信息及路径校验；明确失败信息。
2. 把清单指定的加载器版本从导入器传递到版本安装入口；补齐 DownloadInfo/Provider 契约，关闭导入流程的自动 API/QSL 附加。
3. 用加载器专用元数据解析替换递归字符串猜测，准确判断已安装版本；先确定共享版本冲突策略。
4. 根据规范筛选客户端文件并处理覆盖目录；保留必要的覆盖优先级规则。
5. 验证已存在及新下载文件，支持下载地址回退；取消在每个阶段传播。
6. 返回成功创建的 `GameData`，只在成功后登记；补齐失败、取消的实例目录和任务收尾。
7. 导出增加文件范围选项、准确的加载器版本、任务进度与取消；保留原子发布和临时文件清理。

建议把导入的明确请求、预览信息和结果放在 `Resource/Pack` 中；由 `ResourceInstallerService` 提供返回 `GameData` 的导入入口，并注入现有管理器，旧静态入口可作为兼容适配器。业务对象不携带 Avalonia 类型，异常继续使用 `OlanException`。

如需要新增或调整后端契约，应先完成后端接口，再接前端。项目必读文档明确要求后端不足以支持解耦时先处理后端，不能在 ViewModel 中拼接协议或增加轮询来绕过。

### 阶段 C：扩展在线整合包检索与安装

此阶段是功能探索建议，不是目录迁移的必要条件。

- 在既有资源检索下拉框中增加“整合包”，保持“搜索框、类型下拉框、搜索按钮”的横向布局；不恢复用户已取消的搜索进度条。
- 后端增加整合包搜索条件及具体发行版查询。搜索结果中的支持 Minecraft 版本与整合包发行版 ID 分开建模；下载用户选定的 `.mrpack` 后进入同一导入流程。
- 使用 `ResourceItem` 的公共展示字段与既有 `ListBox Classes="card-list"` 结果卡片，复用旧请求取消与结果防覆盖机制。
- 整合包安装会创建新实例，不能照搬模组/光影“选择已有目标实例”的流程。建议新增 `InstallPackPane`，提供包版本、实例名称、Minecraft/加载器信息、安装和取消；本地导入也可以进入这个 Pane。
- Pane 使用 `PaneHeader`、`pane-surface`、`pane-field`、任务状态样式及注入工厂。支持版本信息继续使用 `ListBox`、透明列表样式和只读设置，并倒序展示。
- 当前共用 `InstallModPaneViewModel.IsShaderPack` 由 `!IsMod` 推导，增加资源类型时必须核对并改为显式类型判断，避免整合包被当作光影。整合包分派到独立工厂，保留模组、光影现有行为。

首个在线来源建议沿用已接入的 Modrinth。其他整合包格式或平台应在统一导入契约稳定后增加适配器，当前代码没有对应实现。
